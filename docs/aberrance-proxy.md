# Локальная модель Aberrant Coding Effort

## Вывод

Точный `% Aberrant BCE` BlueOptima локально воспроизвести нельзя: формула, набор языковых анализаторов, внутренние бенчмарки и пороги не опубликованы. Публично подтверждена общая конструкция: Coding Effort строится из изменений до 36 статических метрик объёма, сложности и взаимосвязанности; ART использует более 20 сравнительных метрик, распределения существующих файлов, абсолютные значения и дельты каждого изменения. Ab.CE — доля Coding Effort, признанная ухудшающей поддерживаемость.^1,2,3

Поэтому Git Calendar считает прозрачный **Aberrant proxy**, повторяющий публично известную форму расчёта, но не имя и не численное значение закрытой модели. Его назначение — показать тренд, проблемный коммит и файл до отправки кода, а не предсказать цифру BlueOptima до десятых долей процента.

## Проверка исходных гипотез

| Гипотеза | Вердикт | Что делает Git Calendar |
|---|---|---|
| Нужно уменьшать связанность | Подтверждено | Считает рост уникальных импортов/зависимостей и сравнивает его с файлами того же языка. Coupling и interrelatedness прямо названы факторами BlueOptima.^2,3 |
| Нельзя переписывать недавно изменённые строки | Как общее правило — неверно | Считает line-churn отдельно: строка, добавленная и затем удалённая/изменённая за 14 дней. Это повод проверить причину, а не автоматический дефект. Относительный churn был связан с дефектностью в исследовании Microsoft, но BlueOptima также обнаружила защитную связь регулярной работы и осмысленного rework в сложных файлах. Сигнал не подмешивается в Aberrant proxy.^4,5,9 |
| Нельзя делать squash | Не подтверждено | Squash не штрафуется. BlueOptima описывает BCE-прорейтинг для крупных накопленных изменений; следовательно, сам размер одного сохранённого коммита предусмотрен моделью.^1 GitClear, напротив, группирует частые коммиты в логические группы и рассматривает это как способ сохранить подробную историю без шума.^6 |
| Чем меньше diff, тем ниже Ab.CE | Недостаточно | Размер изменения влияет на Coding Effort, но workflow-факторы существенно слабее предсказывают maintainability, чем качество состояния файлов. Маленький commit может ухудшить сложную функцию; большой рефакторинг может улучшить файл.^2 |
| Тесты автоматически снижают Ab.CE | Не подтверждено | Отсутствие тестов остаётся отдельным советом. Тестовые файлы не дают искусственный «бонус» Aberrant proxy. |

Практический вывод: снижать нужно не число коммитов и не объём видимой активности, а ухудшение структуры конкретных файлов — сложность управления, зависимости, размер обязанностей, длину функций и читаемость. Рефакторинг, который уменьшает плохой показатель, не считается нарушением даже тогда, когда файл пока остаётся сложнее среднего.

## Публично известная модель BlueOptima

BlueOptima разделяет несколько понятий:

- `ACE` оценивает интеллектуальное усилие изменения, включая новый код, рефакторинг и удаление кода.
- `BCE` корректирует накопленные крупные изменения и распределяет effort по активным дням. Публично указан дневной максимум 5 единиц и прорейтинг не более чем на девять активных дней.^1
- `DART` оценивает maintainability изменений разработчика; `FLART` — состояние файла после коммита.^2
- `Ab.CE` — доля Coding Effort, которую DART признал aberrant.^2

В документах разных лет встречаются формулировки «более 20» и «26» метрик для ART, а для Coding Effort — «до 36». Это не ошибка локальной модели: публичное описание продукта менялось. Стабильной остаётся схема `распределение файлов → относительные пороги → абсолютное значение и дельта → количество и тяжесть нарушений`.^2,3

BlueOptima публично перечисляет характерные проблемы: высокий LOC, длинные сложные функции, большое число сложных функций, высокая цикломатическая сложность, межклассовые зависимости, coupling, неэффективная структура файла, недостаточное объяснение, избыточные комментарии, сложные запросы и сложный control flow. На более высоком уровне они группируются в God Class, File Complexity, Lack of Code Readability, Functionality Overload и Factory Method Symptom.^2

## Формула Git Calendar

### 1. Отбор данных

- История читается из выбранных refs, но merge-коммиты всегда исключаются.
- Автор фильтруется только по явно введённым имени/email; глобальная Git-конфигурация не читается.
- Binary, generated, vendor, mocks, Pods и `node_modules` исключаются.
- Глубокий анализ ограничен последними 180 днями, 240 новейшими подходящими коммитами и 12 крупнейшими исходными файлами одного коммита. Покрытие показывается рядом с результатом.

Ограничение необходимо, чтобы периодическое локальное сканирование десятков репозиториев оставалось предсказуемым. Неохваченные коммиты не получают нулевой риск: они исключаются из знаменателя Aberrant proxy.

### 2. Coding Effort proxy

Для коммита рассчитывается:

```text
CE = min(12,
    0.30
  + log2(1 + meaningful changed source lines) / 2.5
  + sqrt(changed source files) × 0.45
  + log2(1 + |Δ cyclomatic complexity|) / 4
  + log2(1 + |Δ dependency count|) / 5
)
```

Это не перевод в реальные часы. Логарифм и квадратный корень подавляют возможность раздувать результат тысячами однотипных строк или файлов.

`BCE/day proxy` — средний `min(5, сумма CE за день)` по будним дням с ненулевым Coding Effort. `ACE/day proxy` — средний фактический CE дня с ненулевым Coding Effort без ограничения 5. Коммиты только с документацией, generated/vendor или binary-файлами остаются видны в календаре, но не получают CE.

### 3. Относительные пороги

Для текущих отслеживаемых файлов каждого языка строится распределение:

- содержательные строки;
- приближённая цикломатическая сложность;
- максимальная вложенность;
- уникальные импорты/зависимости;
- число функций;
- максимальная длина функции;
- доля строк длиннее 120 символов;
- доля комментариев.

Рабочий порог — 90-й перцентиль языка в конкретном репозитории, но не ниже консервативного абсолютного минимума. Выбор 90-го перцентиля — **наша явная эвристика**, а не раскрытый порог BlueOptima. При выборке менее восьми файлов применяется только абсолютный минимум.

### 4. Анализ изменения до/после

Для каждого затронутого файла Git Calendar получает состояния `commit^:path` и `commit:path`. Сигнал создаётся, когда значение после коммита:

1. оказалось выше относительного порога; и
2. пересекло порог либо ухудшило уже плохое значение минимум на 5%.

Если коммит уменьшает плохое значение, он получает отметку улучшения, но не aberrant-риск по этой причине. Это важно для безопасного рефакторинга legacy-кода и соответствует публичному описанию ART, где учитываются и абсолютные значения, и дельты.^3

Тяжесть отдельного нарушения растёт с превышением порога и ограничена. Несколько нарушений объединяются вероятностным дополнением, чтобы результат оставался в диапазоне 0…1 без простого суммирования выше 100%.

### 5. Aberrant proxy

Риск коммита — среднее рисков затронутых файлов, взвешенное по числу изменённых строк этих файлов. Итог:

```text
Aberrant proxy % = Σ(CE commit × risk commit) / Σ(CE analyzed commit) × 100
```

Публичные зоны BlueOptima (`Best < 5%`, `Requires Improvement > 13%`) можно использовать только как ориентир для направления. Они не калибруют локальную формулу и не превращают её результат в настоящий Ab.CE.^2

### 6. Краткосрочный line-churn

Git Calendar читает patch-историю без merge-коммитов, нормализует содержательные строки и связывает добавление с последующим удалением той же строки в том же файле в течение 14 дней. Перемещение неизменной строки внутри одного коммита не считается churn.

Метрика намеренно отдельная. GitClear распределяет effort свежей строки между связанными коммитами и использует churn как показатель повторной работы.^5 Microsoft Research показала, что относительные churn-метрики могут быть полезными ранними индикаторами дефектности, но абсолютный churn сам по себе слаб.^4 При этом BlueOptima обнаружила, что частая работа и rework в потенциально рискованных файлах могут снижать Change Failure Rate за счёт знания контекста.^9 Поэтому от 5% приложение предлагает проверить причину, но не окрашивает churn как aberrant-риск.

### 7. Средний интервал коммитов

Коммиты сворачиваются в уникальные календарные дни выбранного часового пояса. Затем берётся среднее число календарных дней между соседними активными днями. Главная карточка использует последние 90 дней, верхняя сводка — только текущий месяц, график — каждый месяц отдельно. Несколько коммитов за один день не улучшают показатель. Merge-коммиты уже удалены на этапе загрузки. Значение выше 2,0 дня подсвечивается красным по заданному продуктовому правилу. Для периода только с одним активным днём показывается отсутствие значения, а не искусственный ноль.

Этот показатель описывает регулярность, а не качество кода и не входит в Aberrant proxy.

## Где прокси всё ещё расходится с BlueOptima

- Анализатор лексический и общий для нескольких языков, а не полноценный AST-анализатор для каждого из более чем 150 форматов.
- Связанность приближена исходящими import/include/require. Вызовы, типы, наследование, runtime coupling и зависимости между пакетами целиком пока не строятся.
- Базовая выборка берётся из текущего checkout. В актуальной публичной документации BlueOptima говорится о калибровке по собственной исторической базе организации; этот слой локально не воспроизведён.^10
- Порог 90-го перцентиля и веса открыты и детерминированы, но не обучены на закрытом наборе BlueOptima.
- Move/copy/find-replace распознаются лишь частично; squash нельзя достоверно восстановить из уже переписанной Git-истории.
- BCE-прорейтинг накопленных изменений воспроизведён только дневным лимитом, без закрытой логики распределения по девяти активным дням.

Главная защита от ложной точности — видимое покрытие. Приложение не включает непроанализированный effort в знаменатель и везде называет результат proxy.

## Полезные следующие функции

Приоритет основан на том, помогает ли функция принять конкретное инженерное решение, оставаясь локальной и проверяемой.

1. **Pre-commit анализ незакоммиченного diff.** Самая полезная следующая функция: показать «что именно стало хуже» до commit/push и сравнить исправление в реальном времени.
2. **Hotspots = частота изменений × структурный риск.** CodeScene использует hotspots как основной способ выбрать маленькую область техдолга с максимальной отдачей; одной карты сложности недостаточно.^7
3. **Temporal/change coupling.** Показывать пары файлов и сервисов, которые постоянно меняются вместе, хотя статически не связаны. CodeScene считает связь по одному коммиту, автору/времени или ticket ID и подчёркивает, что сама связь требует контекста, а не является автоматическим дефектом.^8
4. **Контекст incident risk.** Добавить возраст файла, накопленный maintainability deficit репозитория и PR time-to-close как отдельные множители приоритета, не смешивая их с Ab.CE. В исследовании BlueOptima 2026 года эти признаки связаны с риском инцидентов, причём PR time-to-close был сильнейшим из перечисленных.^11
5. **Калибровка по экспорту BlueOptima.** Импорт CSV с реальным DART/Ab.CE позволил бы подобрать веса на данных конкретной организации и показывать ошибку прогноза вместо уверенной выдуманной цифры.
6. **Профили языков на AST/tree-sitter.** Начать с Go, Swift и TypeScript: точные функции, cyclomatic/cognitive complexity, package fan-in/fan-out, public API surface, дублирование блоков.
7. **Commit groups вместо борьбы со squash.** Группировать save-point коммиты по branch/ticket/time/переписанным строкам и оценивать итоговый logical diff. Это сохраняет полезный blame и даёт компактный обзор.^6
8. **Настраиваемые ignore-правила и маркеры generated.** Без этого protobuf, mocks, миграции и vendored code будут создавать шум в любом универсальном анализаторе.
9. **Экспорт JSON/CSV и сравнение периодов.** Нужны формула, версия анализатора, покрытие, диапазон и список коммитов, чтобы результат можно было воспроизвести.
10. **Опциональная PR/Jira-корреляция.** Размер PR, review cycles и ticket ID полезны для процесса и change coupling, но должны быть отдельным слоем: публичное исследование BlueOptima показывает, что workflow-факторы слабее файловых для прогноза maintainability.^2

Не стоит приоритизировать искусственные streak-награды, советы «делайте больше коммитов», штраф за squash или объединённый магический score без детализации. Такие функции легко оптимизировать в ущерб коду.
